> 여기는 **규칙**만. 사실은 `docs/SITE_FACTS.md`, 계획은 `AEO_PLAN.md` / `DESIGN_PLAN.md`.

## 1. 이 프로젝트

- **대상**: 아이원소프트뱅크 홈페이지. 클래식 ASP(.asp), IIS 구동.
- **이 폴더**: `C:\_` — 라이브 사이트 소스
- **디자인 참조**: `C:\soft_bank-main` — 디자이너가 **현재 수정 중**인 디자인 파일. 읽기 전용으로 참조만 한다. **절대 수정하지 않는다.**
- **배포**: git push가 아니라 **FTP 업로드**. 커밋 ≠ 배포. 항상 두 단계로 생각한다.

**동시에 진행되는 작업 두 줄기** (`AEO_PLAN.md`, `DESIGN_PLAN.md`):
1. SEO / AEO / GEO — 구조화 데이터, 메타, 크롤러 정책, 답변형 콘텐츠
2. 디자인 개편 — 디자이너 작업물을 ASP 템플릿에 반영

둘이 **같은 파일(`head.asp`, 공통 include)을 건드린다.** 순서를 잘못 잡으면 서로 덮어쓴다.
작업 전에 `DESIGN_PLAN.md`의 "SEO 작업과의 충돌" 절을 확인한다.

## 2. 작업 시작 전에

1. `docs/SOURCE_MAP.md`가 있으면 먼저 읽는다. 없으면 만드는 것이 첫 작업이다.
2. 해당 계획서(`AEO_PLAN.md` 또는 `DESIGN_PLAN.md`)의 현재 상태와 다음 액션을 읽는다.
3. 사실 관계(회사명·전화·URL·제품명)는 **추측하지 말고** `docs/SITE_FACTS.md`에서 가져온다. 없으면 코드에서 확인하거나 사용자에게 묻는다.
4. **파일을 고치기 전에 그 파일을 읽는다.** 특히 `head.asp`는 여러 태그를 동적 생성하므로 "없다"고 단정하기 전에 조건 분기를 전부 확인한다. (과거 외부 진단이 이걸 놓쳐 오진단한 이력 있음)

## 3. 절대 하지 말 것

**파일 안전**
- `C:\soft_bank-main`의 파일을 **수정하지 않는다.** 디자이너가 작업 중이다. 읽기만.
- **인코딩을 깨뜨리지 않는다.** ASP 파일은 EUC-KR일 수 있고 디자인 파일은 UTF-8일 가능성이 높다. 저장 전에 원본 인코딩을 확인하고 동일하게 유지한다. **확인 없이 일괄 치환(sed 등) 금지.** 한글이 `?????`로 깨지면 되돌리기 어렵다.
- **커밋되지 않은 변경 위에 큰 작업을 시작하지 않는다.** `git status`로 확인하고, 깨끗하지 않으면 먼저 커밋하거나 사용자에게 알린다.
- 공통 include(`head.asp` 등)를 고칠 때는 **그 파일을 쓰는 모든 페이지**에 영향이 간다는 것을 전제로 한다. 어느 페이지들이 영향받는지 먼저 센다.

**SEO 원칙**
- **가짜 데이터로 스키마를 채우지 않는다.** `aggregateRating`, `review`, `price`를 실제 근거 없이 넣지 않는다.
- **화면에 없는 내용을 JSON-LD에 넣지 않는다.** 비공개·임시저장 게시물이 스키마에만 들어가는 경우 포함.
- 키워드 스터핑, 클로킹, 숨김 텍스트, 자동 생성 대량 페이지를 만들지 않는다.

**기타**
- **한 커밋에 여러 목적을 섞지 않는다.** 디자인 / 스키마 / robots 정책 / 콘텐츠는 각각 별도 커밋.
- 하드코딩된 DB 접속정보·API 키를 **출력하거나 커밋하지 않는다.** 발견하면 위치만 보고한다.
- 사용자 결정 대기 항목은 커밋에 포함하지 않는다.

## 4. 주장하기 전에 검증하는 기준

| 종류 | 예시 | 검증 |
|---|---|---|
| **시간에 따라 변하는 정책 사실** | 리치 결과 지원 여부, 검증 도구의 검사 범위, 크롤러 User-Agent 이름, API 스펙 | **웹 검색으로 확인한 뒤에만 주장한다.** 출처 URL을 남긴다 |
| **안정적 스펙 정의** | schema.org 타입의 의미, HTTP 상태 코드, CSS 속성 동작 | 검증 생략 가능 |

> 사례: "Rich Results Test로 FAQ 자격을 확인할 수 있다"는 주장이 검증 없이 나왔다가 오류로 판명됨(FAQ 리치결과는 2026-05 중단, 06월 RRT 지원 제거). **도구의 기능·범위도 정책 사실로 취급한다.**

## 5. 검증 도구 역할 분담

| 도구 | 용도 | 주의 |
|---|---|---|
| `validator.schema.org` | **문법 검증 전용.** 모든 타입 | 리치 결과 자격은 알려주지 않음 |
| Google Rich Results Test | **살아있는 리치 결과 유형**의 자격 검증 (BreadcrumbList, Organization 등) | FAQ/HowTo는 **여기서 안 뜨는 게 정상.** 버그 아님 |
| Search Console URL 검사 | 실제 색인 상태·렌더링 | 라이브 URL 필요 |
| 네이버 서치어드바이저 | 네이버 색인·수집 | 구글과 별개로 반드시 확인 |

FAQPage는 `validator.schema.org`로만 확인한다.

## 6. 스키마 작성 규칙

- JSON-LD만. Microdata/RDFa 혼용 금지.
- `@id`로 엔티티를 고정하고 재사용한다 (Organization은 `https://<도메인>/#organization` 하나만 두고 다른 스키마에서 참조).
- `canonical`과 스키마의 `url`은 항상 일치.
- 페이지당 의미 있는 타입만. 중복·과잉 마크업은 신호를 희석한다.

## 7. 디자인 작업 규칙

- 디자이너 HTML을 ASP에 옮길 때 **ASP 로직(`<% %>`), include, DB 바인딩을 먼저 추출해 보존**한다. 통째로 덮어쓰지 않는다.
- 템플릿을 교체하면 기존 SEO 자산(JSON-LD, canonical, meta, OG)이 날아간다. **교체 전에 목록을 뽑아두고, 교체 후 하나씩 복원 확인**한다.
- 시맨틱을 유지한다. `h1`은 페이지당 하나, 헤딩 계층을 건너뛰지 않고, `img`에 `alt`를 남긴다. 디자이너가 전부 `div`로 만들었으면 시맨틱 태그로 올려준다.
- 한 번에 전체를 바꾸지 않는다. **한 페이지씩, 검증하고 다음으로.**

## 8. 커밋

- 한글 메시지, `영역: 무엇을 왜` 형식
  - `design: 메인 비주얼 섹션 신규 디자인 반영 (ASP include 구조 유지)`
  - `schema: faq_view.asp QAPage→FAQPage 교체 (UGC 타입 오용 수정)`
- 커밋 후 해당 계획서의 체크박스와 "현재 상태"를 갱신한다. **계획서가 진실의 원본이다.**
- FTP 업로드 후에는 라이브 검증 결과를 계획서 진행 기록 표에 적는다.

## 9. 응답 방식

- 불확실하면 확실한 척하지 말고 "확인 필요"로 표시한다.
- 파일을 수정했으면 **어떤 파일의 어느 부분을 왜** 바꿨는지 한 줄로 남긴다.
- 코드를 읽지 않고 추정으로 답하지 않는다.
- 되돌리기 어려운 작업(여러 파일 일괄 수정, 템플릿 교체) 전에는 **먼저 알리고 확인받는다.**
