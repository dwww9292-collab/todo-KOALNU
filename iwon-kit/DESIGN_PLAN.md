## 1. 디자인 파일 성격 파악 `<미작성>`

먼저 `C:\soft_bank-main`이 **무엇인지** 확정해야 한다. 이게 전체 작업량을 결정한다.

- [ ] 정적 HTML/CSS 묶음인가, 빌드 결과물(dist)인가, 소스(React/Vue 등)인가
- [ ] 어떤 템플릿·프레임워크 기반인가 (Bootstrap? Tailwind? 자체?)
- [ ] `-main` 접미사 → GitHub ZIP 다운로드로 보임. 원본 저장소가 어디인가 (디자이너에게 확인)
- [ ] 반응형인가. 브레이크포인트는 몇 개인가
- [ ] 외부 CDN 의존이 있는가 (폰트, 아이콘, JS 라이브러리)
- [ ] **파일 인코딩** — UTF-8일 가능성이 높다. ASP 측과 다르면 변환 규칙을 먼저 정해야 한다

> **왜 먼저 확인하나**: 빌드 결과물이면 디자이너가 수정할 때마다 다시 받아야 하고, 소스면 빌드 파이프라인을 ASP 사이트에 어떻게 붙일지 결정해야 한다. 완전히 다른 작업이 된다.

## 6. SEO 작업과의 충돌 ⚠️

두 작업이 **같은 파일을 건드린다.** 이게 이 프로젝트의 핵심 리스크다.

| 파일 | 디자인 작업 | SEO 작업 | 충돌 |
|---|---|---|---|
| `head.asp` | 상단 마크업·CSS 링크 교체 | hreflang 삭제, 스키마 추가 | **직접 충돌** |
| `faq.asp` | FAQ 목록 레이아웃 | FAQPage JSON-LD, 비공개 필터 | **직접 충돌** |
| `brand.asp` | 브랜드 페이지 레이아웃 | SoftwareApplication, Service 스키마 | **직접 충돌** |

### 권고 순서

```
1. git init + 기준점 커밋          ← 선행 조건
2. docs/SOURCE_MAP.md 작성          ← 현재 구조 파악
3. SEO P0 작업 완료 + FTP + 검증    ← 작은 변경, 빨리 끝남 (반나절)
4. SEO 자산 스냅샷 저장
5. 디자인 개편 — 한 페이지씩
6. 페이지마다 SEO 자산 복원 확인
7. 디자인 완료 후 SEO P2 착수
```

**근거**: SEO P0은 반나절이면 끝나는 작은 변경이다. 먼저 끝내고 **검증까지 마쳐 기준선을 만든** 다음 디자인을 올리면, 뭔가 깨졌을 때 원인이 디자인 쪽임을 바로 안다. 순서를 뒤집으면 두 변경이 뒤섞여 분리가 불가능해진다.

**단, 디자인 교체 범위가 `head.asp` 전체에 걸치면** SEO P0의 `head.asp` 작업(hreflang 삭제)은 디자인 반영 **직후**로 미루는 게 낫다. 어차피 다시 쓸 파일을 두 번 고칠 이유가 없다. 1절·3절이 채워지면 이 판단을 확정한다.

## 7. 작업 순서 제안 `<미작성>`

1절~6절이 채워진 뒤 작성한다. 원칙:

- **한 페이지씩.** 전체를 한 번에 바꾸지 않는다
- 영향 범위가 **좁은 페이지부터** 시작해 공통 영역은 마지막에 (또는 가장 신중하게)
- 페이지 하나 = 커밋 하나 = FTP 업로드 하나 = 검증 하나
- 공통 영역 교체는 **별도 커밋**으로 분리하고, 영향받는 페이지를 전수 확인
