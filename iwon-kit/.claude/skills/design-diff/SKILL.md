# 디자인 대조 및 계획 수립

목적: **코드를 고치지 않고** `DESIGN_PLAN.md`를 채운다. 이 스킬은 조사와 계획만 한다. **수정은 하지 않는다.**

## 0. 전제 확인 (먼저)

- [ ] `C:\_`가 git 저장소인가 — `git status`. 아니면 **중단하고** `START_HERE.md` 0단계를 사용자에게 안내한다. 버전관리 없이 개편 계획을 세우는 것은 의미가 없다
- [ ] 작업 트리가 깨끗한가 — 커밋 안 된 변경이 있으면 알린다
- [ ] `C:\soft_bank-main`에 접근 가능한가 — VSCode 작업 영역에 추가돼 있어야 한다. 없으면 사용자에게 추가를 요청한다
- [ ] `docs/SOURCE_MAP.md`가 있는가 — 없으면 그것을 먼저 만든다

> **`C:\soft_bank-main`은 절대 수정하지 않는다.** 디자이너가 작업 중이다. 읽기 전용.

## 1. 디자인 파일 성격 판정

이게 전체 작업량을 결정하므로 먼저 확정한다.

- 루트의 파일 구성을 본다 — `package.json`이 있으면 소스, `index.html` + `assets/`만 있으면 정적/빌드 결과물
- `-main` 접미사는 GitHub ZIP 다운로드 흔적이다. 원본 저장소를 물어볼 항목으로 기록
- CSS 프레임워크 식별 — 클래스명 패턴으로 판단 (`col-md-`→Bootstrap, `flex items-center`→Tailwind)
- 외부 CDN 의존 목록 — `<link>`, `<script src>` 중 외부 도메인
- **인코딩 확인** — 파일 앞부분 바이트와 `meta charset`. ASP 측과 다르면 변환 규칙이 필요하다
- 반응형 브레이크포인트

판정 결과를 `DESIGN_PLAN.md` 1절에 쓴다.

## 2. 페이지 대응표 작성

디자인 파일 목록과 ASP 파일 목록을 나란히 놓고 대응을 찾는다.

- 파일명만으로 짝짓지 말고 **내용(제목, 본문)으로 확인**한다
- **1:1이 아닌 경우를 반드시 표시한다**:
  - 디자인에만 있는 신규 페이지 → 새로 만들 것인가
  - ASP에만 있고 디자인에 없는 페이지 → 유지인가 폐기인가 (사용자 확인 필요)
  - 디자인 1개가 ASP 여러 개에 대응 (목록/상세) 또는 그 반대
- 변경 범위를 전체교체 / 부분 / 신규로 분류

`DESIGN_PLAN.md` 2절에 쓴다.

## 3. 공통 영역 식별 — 가장 위험한 부분

`head.asp`, 상단 GNB, 푸터, 사이드바가 각각 어느 파일이고 **몇 개 페이지에서 include 되는지 센다.**

```
grep -rl "head.asp" --include=*.asp .
```

영향받는 페이지 수를 숫자로 적는다. "여러 개"가 아니라 "17개"로.

`DESIGN_PLAN.md` 3절에 쓴다.

## 4. 보존 자산 추출 — 덮어쓰면 날아가는 것

### ASP 자산
- `<% %>` 로직 블록 — 어느 파일에 무엇이
- `include` 지시자
- DB 바인딩 — 디자인의 더미 텍스트 자리가 실제로는 DB에서 와야 하는 곳
- 폼 action / 히든 필드 / 서버 검증
- 세션·인증 체크

### SEO 자산
`DESIGN_PLAN.md` 5절 표의 항목을 전부 찾아 **위치(파일:라인)를 기록**한다.
그리고 **실제 내용을 `docs/SEO_ASSETS_SNAPSHOT.md`로 저장**한다.
교체 후 기억에 의존하지 않고 이 파일과 대조한다.

### 비밀값
하드코딩된 DB 접속정보·API 키를 찾으면 **위치만** 보고하고 `.gitignore`에 추가를 제안한다.
**값을 출력하거나 커밋하지 않는다.**

`DESIGN_PLAN.md` 4·5절에 쓴다.

## 5. SEO 작업과의 충돌 판정

`AEO_PLAN.md`의 작업 대상 파일과 2·3절의 디자인 변경 대상 파일을 교집합 낸다.
겹치는 파일마다 어느 쪽을 먼저 할지 판단해 `DESIGN_PLAN.md` 6절을 확정한다.

판단 기준:
- 해당 파일이 **디자인으로 전체 교체**된다면 → SEO 작업은 교체 **후**로 미룬다 (두 번 고칠 이유 없음)
- 디자인 변경이 **부분**이고 SEO 작업과 다른 영역이면 → SEO 먼저 (작고 빨리 끝나므로 기준선 확보)

## 6. 작업 순서 제안

원칙:
- **한 페이지 = 한 커밋 = 한 FTP 업로드 = 한 검증.** 묶지 않는다
- 영향 범위 좁은 페이지부터. 공통 영역은 가장 신중하게
- 공통 영역 교체는 별도 커밋, 영향받는 페이지 전수 확인

`DESIGN_PLAN.md` 7절에 쓴다.

## 7. 미확인 항목 정리

디자이너·담당자에게 물어볼 것을 `DESIGN_PLAN.md` 9절에 모은다. 특히:
- 디자인 작업이 언제 끝나는가 (작업 중인 파일을 반영하면 또 바뀐다)
- 반영해도 되는 페이지와 아직 작업 중인 페이지 구분
- 디자인에 없는 기존 페이지 처리 방침

## 8. 마무리 보고

사용자에게 이렇게 보고한다:

1. 디자인 파일이 **무엇인지** (1절 판정 결과) — 한 줄
2. 총 작업 규모 — 페이지 수, 전체교체/부분 비율, 공통 영역 포함 여부
3. **가장 큰 리스크 3개** — 구체적으로. "인코딩 주의" 같은 일반론 말고 "ASP는 EUC-KR인데 디자인은 UTF-8이라 전 파일 변환 필요" 처럼
4. 먼저 해야 할 것 1개
5. 사용자 확인이 필요한 결정 사항

**코드는 고치지 않았음을 명시한다.**
